Execution lanes

  1. Inventory and preserve. Export all 767 paths, sizes, source URLs, and SHA-256 digests. Keep the Vercel token and objects unchanged.
  2. Create and copy. Create the exact NYC3 bucket, upload every object under its unchanged key with public-read ACL, then compare counts, sizes, and SHA-256 readbacks.
  3. Change the authority. Replace source-level Vercel fallbacks and hardcoded URLs with a single configurable Spaces base URL; add behavior tests first.
  4. Critic gate. A fresh critic receives only the diff, oracle, and copy receipt. No cutover with a blocking finding.
  5. Deploy and prove. Merge, observe the DO deployment, test home/explore/direct+navigated reader, inspect browser/network content origins, and probe a representative corpus.
  6. Start soak. Record the two-clock start only if no production path reads Vercel. Do not delete Vercel assets or project in this lane.

Acceptance oracle

  • Source and destination manifests contain exactly the same 767 keys and sizes.
  • Every object has matching SHA-256 content on Vercel and Spaces.
  • Production source, environment, rendered HTML, and reader network paths contain no Vercel Blob origin.
  • Home, Explore, and the direct and navigated Iliad reader remain healthy while core Sanctum/Powder checks stay green.
  • Rollback values and the untouched Vercel store are recorded in the receipt.

Stop conditions

Stop before cutover for a missing object, hash mismatch, non-public destination read, production regression, core-service degradation, or blocking critic finding. Roll back the application base URL immediately if post-deploy origin or reader checks fail.
